## 1. 目标与范围

在 hadoop102 的独立实验环境中，读取 MovieLens-32M 全部评分，以固定的 **k=100、beta=0、好评阈值 rating≥4.0** 构建一份可供后续系统接入的电影邻居模型。先修好持续资源保护，再做全量输入下的分块预检，通过后自动继续正式训练；资源不足则有据可查地停止。

本轮交付是**经过正确性核验、尚未发布的全量模型文件**。不继续调 ALS，不搜索 ItemCF 参数，不修改在线服务、数据库表或推荐页面，不实现 genres 调查，不增加关键词或混合算法。

全量模型使用所有有效历史评分，不做留出；它服务于后续部署，**不在训练数据上报告 NDCG/Recall 来证明效果**。论文效果引用已有探索和新用户确认实验。全量效果是否提升不属于本轮结论。

## 2. 现有依据与必须修正的问题

确认实验 `experiments/itemcf/out/confirmation/20261004T100122Z/`：20,000 名用户，2,565,050 条训练评分，1,953 名有效评测用户；ItemCF NDCG@20=0.1274668036、Recall@20=0.1411371143，均超过两个热门基线。无需重复参数搜索。

但原实现存在两个全量运行前必须处理的工程问题：

1. `confirm.py` 的资源采样由主计算流程调用。记录总共只有 8 个采样点，构图约 493 秒没有采样。325,914,624 字节只是**已采样最大 RSS**（约 326 MB / 311 MiB），不是真实峰值证明，且构图期间无法及时触发终止。正式计算约 587 秒，数据准备另约 613 秒，不能把总流程写成 10 分钟。
2. `build_graph_csr` 虽然分块计算共现，但仍调用 `core.build_neighbors` 返回整张 Python 字典图，再建立 `by_source` 和最终数组；输入也先累积 COO 分块再 concatenate。全量时这些并存对象可能抬高峰值，不能直接按产物大小外推内存。

旧结果文件保持原样；在新报告中说明上述限制。已有源码注释与实际行为冲突时，以执行代码为准。

## 4. 模型固定规则与产物契约

`X[u,i]=1` 当且仅当该用户给电影 i 的评分 ≥4.0。电影全集取全部合法评分中出现过的电影，包含没有好评的电影。

```text
n_like(i) = sum_u X[u,i]
c(i,j)   = sum_u X[u,i] * X[u,j]
s(i,j)   = c(i,j) / sqrt(n_like(i) * n_like(j))
```

对角线为 0；零共现、零好评支持度时相似度为 0；只存正相似邻居。每个来源 i 按 `(-similarity, target_movieId)` 升序保留最多 100 条，不做双向补边或热门补齐。计数 int64、相似度 float64，禁止 bool/uint8 共现计数。新图分数是排序依据，不是五星预测评分。

建议用独立 NumPy 数组保存模型，避免全图 Python dict 和解压峰值：

| 文件 | 内容 |
|---|---|
| `model/item_ids.npy` | 递增 movieId，int64 |
| `model/indptr.npy` | 每个来源的邻居边界，int64，长度物品数+1 |
| `model/target_indices.npy` | 目标在 item_ids 中的索引，int64 |
| `model/similarities.npy` | 按来源、邻居排名排列的 float64 相似度 |
| `model/cooccurrences.npy` | 对应边的 int64 共现数 |
| `model/n_like.npy`、`model/n_all.npy` | 对齐 item_ids 的好评人数、全部评分人数 |
| `model/model.json` | schema_version=1、模型 ID、来源指纹、参数、计数、dtype、文件哈希、构建时间、状态 |

没有邻居的来源保留空区间。读取时用 mmap，验证结构和哈希后再使用。schema 写清楚索引语义、排序和零邻居行为。原子写元数据，只有全部检查通过才标记 `validated_unpublished`；这个状态不代表线上 active。

### A. 修好资源保护

- [ ] 监督程序启动计算子进程，Linux 使用独立会话/进程组；每 **2 秒**采样一次根进程及后代，去重 PID 后求和 RSS，同时记录 MemAvailable、swap、阶段和时间。监督本身不受工作进程阻塞；`resources.csv` 持续刷盘。
- [ ] 规则：工作进程树 RSS > **3 GiB**、MemAvailable 连续 **30 秒** < **256 MiB**、剩余磁盘 < **2 GiB**或阶段超时，先发 TERM，10 秒未退出再 KILL，只终止本轮拥有的进程组。监督失败、长时间无法采样应停止工作并记监控失败，而非继续无保护运行。
- [ ] 测试一个不回调监控的阻塞 worker，证明仍能定时采样并按短测试超时终止；用可注入的资源读数验证 30 秒持续条件、恢复后重计时、子进程内存汇总和其他进程不受影响。用小阈值测试，不真的耗尽机器内存。
- [ ] 单独记录“采样最大值”，即使 2 秒采样也不叫精确连续峰值。测试退出码、失败原因、正常退出和子进程清理均有终态。

### B. 低内存精确构图与等价性

- [ ] 流式记录用户/物品索引、n_all/n_like 和每用户好评数；两遍扫描预分配磁盘数组/CSR。避免整份 Python 四元组、全量 pair 集合和 concatenate 的多份临时副本。磁盘 mmap 仍可能增加 RSS，必须纳入监督。
- [ ] 用完整好评矩阵计算列块 `X[:, start:stop].T @ X`；全量 n_like 用于归一化。每块计算相似度、按规则取 top-100 后立刻写有序数组/块文件并释放临时对象，不保留整张 dict 图。不能按用户批次独立归一化后拼图，不能减少候选或截断用户历史。
- [ ] 图边文件按块落盘便于验收和失败留档，默认不实现复杂自动续跑。失败块与成功块有记录；禁止拼入来源/参数/源码不同的旧块。
- [ ] 测试手算共现、260 人计数防溢出、同用户跨输入块、重复评分拒绝、零好评来源、相似度平票、存取回环以及 block_size=16/32/64/128 的等价性。
- [ ] 用旧 2k 的固定训练段（196,614 行，64/16/20 切分）构图，对照 `fix14` 的最佳 k=100/beta=0 推荐：1,930 用户 ID/推荐次序完全一致，分数差 ≤1e-9，NDCG/Recall 差 ≤1e-10。该对拍只验证实现等价，不计为新的推荐效果实验。旧产物先冻结哈希，不假定 git HEAD 就是运行代码。

### C. 全量资源预检与自动继续规则

- [ ] 新 run 下先保存参数、输入指纹、源码归档/哈希、Git HEAD 与 dirty、解释器及依赖版本、机器与磁盘信息、完整命令。环境预检要求可用磁盘至少 **10 GiB**；同时估算磁盘中间件需求，若估算加 2 GiB 余量超过可用空间则不启动。保留旧产物，不通过删除腾空间。
- [ ] 在监督下构建**完整数据的**好评 CSR，记录索引准备和 CSR 转换阶段的时间/内存。准备阶段预算 **60 分钟**，失败即停止，不能只测一小片矩阵后宣称全量可行。
- [ ] 使用完整矩阵，选取物品 ID 首/中/末、好评支持度最高物品所在块，以及两个按固定哈希选出的不同块，共最多六块。初始列块为 128，测试真实共现、top-k 与写盘耗时，不读取新的推荐效果指标。
- [ ] 预检预算 **30 分钟**。128 列因临时内存不足时，可自动按 64→32→16 递减重试，每次记录失败；若基本 CSR 本身已超限，减列块无效，应停止。最多一次逐级尝试，公式/k/数据保持不变。
- [ ] 用预检各块耗时的均值和最大值分别乘预计块数给出粗估范围，并计入模型装配与验证预留时间。块难度差异大，必须说明不是可靠运行时上界。通过条件：无监控缺口、完整矩阵可装载、预计磁盘够用、保守估计可在 **4 小时正式阶段预算**内完成。
- [ ] 通过则直接执行正式构图，不要求用户再次确认；明显超预算或硬性资源不足则停止并输出 `resource_blocked`。不擅自转云、付费、升级 VM 或改采样规模。成功预检块只有在同一冻结输入/配置/源码且验证完整时才允许复用，否则全部重新生成。

### D. 正式全量训练与核验

- [ ] 在同一个独立环境按选定的工程块大小构图，全程保持资源监督；正式阶段包含图装配、压缩（若采用）、哈希和核验，总预算 4 小时。任一阶段超限即记录失败，不把残缺模型标记成功。
- [ ] 核验全部来源和边：索引范围、indptr 单调与终值、无自环/重复目标、每来源 ≤100、相似度有限且在 (0,1]、按相似度降序和真正浮点平票 movieId 升序、共现为正且不超过两端 n_like。
- [ ] 固定 seed=42 抽 100 个有邻居的来源（不足则全部），从完整训练评分独立重算这些来源对所有电影的共现、相似度和 top-100，核对目标 ID/顺序及分数。覆盖高/低支持度与并列边界来源，不仅核对已经保存的正边，否则无法发现漏掉更优邻居。
- [ ] 模型重新 mmap 加载并与写入前统计/哈希核对。用固定的少量 MovieLens 历史画像检查推荐排除已看、低分不作为正向来源、无好评时返回空、分数可由贡献重算；不把这些训练画像当离线泛化评测。
- [ ] 运行结束核对源码及输入指纹未漂移；父 run ID、model ID 和产物中的 ID 必须一致，不能仍写成通用 `run`。在本地同步模型、报告和核验文件，不同步凭据或原始 32M CSV。

## 6. CLI 与产物（需实施，当前不是可运行命令）

实现后必须提供一个受监督的编排入口，示例契约：

```bash
/home/h/venvs/itemcf/bin/python -m experiments.itemcf.full_train \
  --input /home/h/movielens/ratings.csv \
  --out /home/h/itemcf_full/<run_id> \
  --max-k 100 --beta 0 --positive-threshold 4.0 \
  --block-size 128 --monitor-interval 2 \
  --prepare-budget-seconds 3600 --precheck-budget-seconds 1800 \
  --train-budget-seconds 14400
```

`<run_id>` 在执行时生成 UTC 时间加短随机标识，独占新目录；命令默认启用监督和先预检后训练，不提供默认绕过保护。运行时 BLAS 相关线程设为 1。实施完成后用 `--help`、测试和冒烟验证实际 CLI，报告记录完整真实命令。

产物：VM `/home/h/itemcf_full/<run_id>/`；本地 `experiments/itemcf/out/full/<run_id>/`。

- `manifest.json`、`source_hashes.json`、源码归档：环境、输入、配置、命令、身份和可复核运行代码。
- `precheck.json`：输入计数、矩阵 nnz、磁盘估算、各块资源/耗时、外推局限、是否继续及原因。
- `resources.csv`、`run.log`、`run_status.json`：每阶段开始/结束/退出码、采样、失败原因；状态只取 running/success/resource_blocked/resource_failed/correctness_failed 等明确值。
- `model/`：第 4 节数组及元数据，只对成功且完整核验的图标记 validated_unpublished。
- `verification.json`：全部结构检查、抽样来源重算、等价性证据、指纹核对。
- `conclusion.md`：一页左右，写清全部评分是否纳入、用户/电影/好评/边数、阶段耗时、采样最大 RSS、覆盖缺口、是否可接入，以及并未进行新的泛化效果评估。
