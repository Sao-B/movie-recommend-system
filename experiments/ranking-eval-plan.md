## 0. 背景与目标

- 系统现状：离线 ALS（active 模型 als-20260915…, rank=50, reg=0.1, RMSE 0.8074）+ 在线 fold-in。
- 待回答的三个问题：
  1. **有效性验证**：现有 HR/NDCG 数字是真偏好信号，还是流行度偏差/泄漏的假象？（对照实验）
  2. **稀疏场景**：站内真实用户只打 3~10 条分时，ALS fold-in 是否输给邻域方法？
  3. **混合收益**：ItemCF+ALS 混合比单独任一方法好多少？（消融表）
- 活人数据现状：user_ratings 仅 22 条（8 号 2 条 + 11 号 20 条全 5 分极端画像），
  11 号不参与任何评估（单一题材 + 零方差，什么也证明不了）。
  → **评估全部基于 ML 虚拟用户，不依赖任何活人。**

## 1. 数据切分（泄漏防护的核心）

| 项 | 口径 |
|---|---|
| 训练切分（80%） | 沿用 train_als.py 的**确定性哈希切分**（与 active 模型同源），约 25,599,242 条 |
| 测试切分（20%） | 约 6,400,962 条，只用于：抽虚拟用户、取真值正例 |
| ALS 因子 | **直接用现网 active 模型**（它就是 80% 训练切分上训出来的，天然无泄漏） |
| ItemCF 相似度表 | **必须只用训练切分建**（这是泄漏防线的关键，见 §4） |

**防泄漏三铁律**（写进脚本注释与论文实验设置一节）：
1. 真值正例只从测试切分取；
2. 虚拟用户的"可见评分"（fold-in 输入）也只从测试切分取（与真值同源但不相交）；
3. ItemCF 相似度表只从训练切分建；全部输入做一遍「movieId ∈ 训练切分物品集」过滤。

## 2. 实验一：打乱对照（证伪实验，最优先）

目的：证明评估协议测到的是**偏好信号**而非数据结构假象。

- 协议：500 个 ML 用户，每人：可见评分 10 条（测试切分内高分+低分混合）、
  真值正例 = 剩余 ≥4.0 分的片（每人最多 10 条）、负例 1000 条
  （从测试切分评分人数 ≥100 的热门池抽，1+n 协议口径）。
- 两跑对比：
  - **A 原始**：可见评分按真实分值喂给 fold-in；
  - **B 打乱**：保留 (u,i) 配对，rating 值随机重排（整体分布不变，偏好关联被摧毁）。
- 判据（数字塌下去 = 协议有效）：
  - A 的 HR@10 显著高于 B（B 应接近随机水平 ≈ 1%）；
  - A 的 NDCG@10 显著高于 B；
  - Spearman：A ≈ 0.7 量级 vs B ≈ 0。
- 附带：Popular 基线（全库按 rating_count 排序取前 10）作为流行度偏差参照系。
- 成本：40 分钟（ratings.csv 扫两遍 + 在线求解 500 用户）。

## 3. 实验二：常数基线（一句话对照）

- 预测恒等于全局均分（movie_rating_stats 精确加权计算），算它的 RMSE。
- 判据：ALS 的 0.8074 必须显著低于它（预期常数基线 ≈ 1.0 量级，即评分标准差）。
- 成本：一条 SQL + 十行代码，并进实验一脚本输出。

## 4. 实验三：稀疏度 × 四方法消融（回答 ItemCF+ALS 值不值）

### 4.1 相似度表构建（新增，scripts/build_item_sim.py）

- 输入：训练切分（HDFS ratings.csv → 按 train_als.py 同款哈希切分过滤）。
- 相似度：cosine，物品向量 = 各用户评分（去均值，减用户均分）。
- 输出：每部片 top-50 近邻 (movie_id, neighbor_id, sim)，
  全库约 440 万行，写 MySQL 新表 `item_similarity`。
- **DDL 变更**：需一张新表（含索引 movie_id, sim DESC）。
  → 属于数据库改动，执行前单独向用户确认。
- 计算路径：PySpark（spark/ 目录新增作业，--master local[*]，与现有训练作业同风格）。
- 成本：Spark 单机几十分钟（2560 万条 × 8.7 万物品）。

### 4.2 四方法 × 四稀疏度

虚拟用户 500 个（测试切分，同实验一池子，便于横向对照），每人四种输入：

| 稀疏度 | fold-in 输入 |
|---|---|
| S3 | 随机 3 条（含高分） |
| S5 | 随机 5 条 |
| S10 | 随机 10 条 |
| Full | 全部可见评分 |

四方法（同一协议、同一真值、同一负例池）：

| 方法 | 打分公式 | RMSE 可报？ |
|---|---|---|
| ALS fold-in | 现网在线链路原样复用（solve_user_vector + rank_unrated_items） | 可（截断后） |
| ItemCF | score(u,i) = Σ_{j∈已评分} sim(i,j)·r_uj，近邻表取 j 的 top-50 | 不可（量纲任意），N/A |
| ALS+ItemCF 混合 | min-max 归一两者分数后 α 混合，α ∈ {0.3, 0.5, 0.7} | 可 |
| Popular | rating_count 降序 | N/A |

输出指标：**HR@10 / NDCG@10 / Recall@10**（主）+ RMSE（仅 ALS 与混合，作参考）。

预期结论形态（跑出来才算数）：
- S3/S5 上 ItemCF ≥ ALS fold-in（邻域在极稀疏下更稳）；
- Full 上 ALS ≥ ItemCF；
- 混合在多数档位不输两者最优者 —— 若不成立，如实报告，不硬撑混合。

### 4.3 报告输出

`scripts/evaluate_ranking.py` 统一产出一张 Markdown 表（论文实验章直接可用）：

```

ALS fold-in   ...
ItemCF        ...
ALS+ItemCF    ...
Popular       ...
随机/打乱对照  ...
```

另附：每档稀疏度的 Top-5 榜单样例（写论文案例分析用）。

## 7. 风险与开放问题

1. **负例池口径**会显著改变 HR 绝对值（9/18 实测：全库随机 0.217 vs 热门池 0.583）。
   计划采用热门池口径（与站内候选门槛语义一致），论文中写明。
2. ItemCF 相似度表用**去均值评分**（减用户均分）——否则热门片相似度虚高，
   整个 ItemCF 通道会退化为 Popular。
3. 混合权重 α 报三个值而非调优挑最好（本科论文不引入"调参"嫌疑）。
4. 时间成本：整个计划不动 Spark 训练、不动在线链路，随时可中断、可回滚
   （回滚 = 不执行 014 迁移 + 删两个新脚本）。
